## 1. Проблема

Крупные языковые модели дорогие по:

- токенам (стоимость API / инференса);
- энергии;
- задержке.

Значимая доля запросов — слабые, шумовые или заведомо низкоуверенные.  
Отправлять их в полную LLM — расточительно.

---

## 2. Решение

**Компактный pre-filter на CPU** перед вызовом LLM:

```
Запрос
  → скоры уверенности (классификатор / ранжирование / эвристики)
  → AI Accelerator LLM Pre-Filter V23
       → REJECT  — не вызывать LLM
       → CLARIFY — запросить уточнение
       → PASS    — вызвать LLM
```

Технологии:

- Numba (int8, parallel, низкая задержка);
- L3 triage (быстрый каскадный отсев);
- логика Гёделя / Лукасевича K=2 (опционально для контекста);
- без обязательной GPU.

## 4. Измеримый эффект (ориентиры с синтетики)

На смешанном потоке (~35% заведомо слабых запросов):

| Batch   | Latency (pre-filter) | Порядок QPS | Доля REJECT |
|---------|----------------------|-------------|-------------|
| 64      | ~0.04 ms             | ~1.5M+      | ~35%        |
| 1024    | ~0.3 ms              | ~3M         | ~35%        |
| 4096    | ~1.2 ms              | ~3.5M       | ~35%        |

**Смысл для заказчика:**  
даже при 20–35% устойчивого REJECT экономия токенов и энергии масштабируется с объёмом трафика.

*Иллюстрация (не гарантия):*  
10M запросов/сутки × 30% REJECT × 1500 tokens ≈ **4.5B токенов** не уходят в LLM.

Реальный % зависит от качества upstream-скоров и порогов `low` / `high`.

---

## 5. Границы и безопасность

- Pre-filter **не заменяет** модерацию и policy-слой.
- Решения детерминированы при фиксированных скорах и порогах.
- Нет сетевых вызовов и «живой» власти в самом модуле — только triage.
- Рекомендуется связка с audit log (request_id, decision, thresholds).

## 6. Минимальное встраивание

```python
from AI_Accelerator_LLM_PreFilter_V23 import AIAcceleratorLLMPreFilter

acc = AIAcceleratorLLMPreFilter(low_threshold=0.30, high_threshold=0.70)
result = acc.filter(confidence_scores)

for i, decision in enumerate(result.decisions):
    if decision == "PASS":
        call_llm(queries[i])
    elif decision == "CLARIFY":
        ask_user_to_clarify(queries[i])
    else:
        return_template_or_cache(queries[i])
```

Вход: матрица скоров уверенности `[n_requests × n_candidates]`.  
Выход: `REJECT` / `CLARIFY` / `PASS` + метрики батча.

---

## 7. Что не обещаем

- «Самый быстрый pre-filter в мире» — нет.
- Нулевую ошибку отсева — нет; нужен подбор порогов на ваших данных.
- Замену полной LLM — нет; это слой **перед** моделью.

---

## 8. Следующие шаги для пилота

1. Подключить реальные скоры (не синтетику).  
2. Разметить 1–2k запросов: должен ли был уйти в LLM.  
3. Подобрать `low` / `high` под precision/recall.  
4. Замерить: % REJECT, false reject, экономию токенов, latency p99.  
5. Решение go / no-go по пилоту.
